# ADR-0003: 所有権を段階的にRAIIへ移行する

- Status: Accepted
- Implementation: In progress

## 背景
`Engine/GameObject.h`では子オブジェクトを`std::list<GameObject*>`で保持し、`Instantiate`が`new`で生成する。解放は`Engine/GameObject.cpp`の再帰的な`Release`/`delete`処理に依存する。`Scripts/State/StateManager.h`も状態オブジェクトをraw pointerで保持している。

## 決定
GameObjectの親子階層や既存の振る舞いを維持しつつ、所有するポインターを段階的にRAII管理へ移行する。参照だけを表す親ポインターなどは非所有参照として区別する。オブジェクトシステム全体の一括置換は行わない。

## 影響
- 所有者と非所有参照の責務を明確にする。
- 変更は境界ごとに進め、シーン破棄・状態切替の順序をテストで保護する。
- 既存の`Release`処理との責務重複を、移行時に整理する。

## 実装時の決定
区切りごとに追記する（①オブジェクトの仕組み、②Engineの資源、③COMと後始末）。

### 所有のルール（全体）
- 所有は`std::unique_ptr`で持つ（共有するものは`std::shared_ptr`、COMは`ComPtr`）。生ポインターは「借りているだけ」で、持ち主より長く持たない。
- 所有を渡す関数は、`std::unique_ptr`を受け取る（呼び出し側が`std::make_unique`で作る）。借りるだけの関数は、生ポインターを受け取る。
- 解放の順序が大事なものは、`Release()`などで明示的に`reset`して、デストラクターに任せない（例：プレイヤーの`StateManager`。`ExitState`がプレイヤーのほかのメンバーを使うため）。
- 子の一覧は`std::list`のままにする（更新中に`Instantiate`で子が増えても、反復が壊れないため）。

### 区切り①（オブジェクトの仕組み）
- `StateManager`: 状態を`unique_ptr`で持つ。`AddState`は`unique_ptr`を受け取り、同じ名前があるときは、渡されたものを破棄してすでにあるものを返す（今までは渡したものが漏れていた）。デストラクターが、名前の順に`ExitState`を呼んでから消す順序は同じ。プレイヤー3種の`StateManager`は`unique_ptr`で持ち、`Release()`で消す。
- コライダー: `GameObject`が`unique_ptr`で持つ。`AddCollider`は`unique_ptr`を受け取り、追加したコライダーを返す。各クラスの`pCollision_`は借りているだけ。
- `GameObject`の子: 親が`unique_ptr`で持つ。`Instantiate` / `InstantiateFront`は、親が必須になった（今までは親なしで呼ぶと、誰も持たなかった。呼び出し側に該当はなかった）。子を親に渡してから`Initialize()`を呼ぶ順序は同じ。`ReleaseSub()`と`KillAllChildren()`は、葉から`Release()`、デストラクターの順序のまま。`ReleaseSub()`を通さずに消した親は、子も消す（今までは子が漏れていた）。`GetChildList()`は、読むだけの型になった。`Main`のルートも`unique_ptr`で持ち、同じ位置で消す。
- Scriptsの持ち主: `StageObjectManager`と`ItemObjectManager`（シーンが持つ）、`UIManager`の`Text`、`AIPlayer`のビヘイビアツリーのノードを`unique_ptr`で持つ。この4種は、今まで解放されていなかった。プレイヤーなどが持っている`ItemObjectManager*`は、シーンから借りているだけ（プレイヤーはシーンより先に消える）。
- 順序は、`Tests/GameObjectTest.cpp`と`Tests/StateManagerTest.cpp`が、更新・描画・解放・破棄のたびに確かめている。

### 確かめたこと（区切り①）
- テストのDebug・Releaseのビルドと全件合格（58件・256の検証）。ゲーム本体のDebug・Releaseのビルド（警告は基線と同じ）と起動。
- シーンを自動で巡回して、落ちないこと（タイトル、ゲーム選択、犬の選択、散歩、ゲームオーバーを2周、10回の切替）。人の入力やコントローラーでシーンが勝手に切り替わらないよう、入力を読まない確認用のビルドで行った。
- 終了時のメモリリーク（CRTのリーク報告）が、61ブロック・4,344バイトから0ブロックになったこと。
- 必須のモデルが欠けたとき（`Floor`、`CollectPlayer`、`AttackPlayer`と`AIPlayer`）に、ダイアログを出して終了コード1で終わり、落ちないこと（ADR-0007の動きのまま）。

### 区切り②（Engineの資源）
- `Model`と`Image`: 一覧を`std::vector<std::unique_ptr<…Data>>`で持つ。同じファイルを読んだものどうしで共有する`Fbx`と`Sprite`は`std::shared_ptr`にした。`Release`の中にあった「ほかで使っていないか」を調べる走査は、いらなくなって消した（最後の1つが手放したときに消える）。
- `Texture`・`Sprite`・`BillBoard`: COMは`ComPtr`で持つ。`Sprite`と`BillBoard`のテクスチャは`unique_ptr`。解放だけのデストラクターと`BillBoard::Release()`を消した。`ComPtr`の使い方は、メンバーへの出力引数に`ReleaseAndGetAddressOf()`、配列やローカルの引数に`GetAddressOf()`、借りるだけの引数に`Get()`。`Texture::GetSampler()`と`GetSRV()`は、`Texture`が持っているものを借りて返すだけ。
- `VFX`: エミッターとパーティクルを`std::list<std::unique_ptr<…>>`、エミッターが持つビルボードを`unique_ptr`にした。`Particle::pEmitter`は借りているだけ（パーティクルが全部消えるまでエミッターは消さない決まりのまま）。`CreateParticle`の引数のイテレーターの型が変わった。`VFX::Release()`は、今まで通りパーティクル → エミッターの順に消す。
- `FbxParts`: マテリアル・頂点・インデックス・骨・ウェイトの配列を`std::vector`、バッファを`ComPtr`、マテリアルのテクスチャを`unique_ptr`にして、デストラクターを消した。配列でなくなったメンバーは名前を変えた（`pVertexData_`→`vertexData_`、`pMaterial_`→`materials_`、`ppIndexData_`→`indexData_`、`ppIndexBuffer_`→`indexBuffers_`、`ppCluster_`→`clusters_`、`pBoneArray_`→`boneArray_`、`pWeightArray_`→`weightArray_`）。`FbxSkin`と`FbxCluster`は、FBXのシーンが持っているものを借りているだけ。
- `Fbx`: FBX SDKのオブジェクトは`delete`でなく`Destroy()`で解放する決まりなので、`Destroy()`を呼ぶ削除関数（`FbxDestroyer`）付きの`unique_ptr`（`FbxUniquePtr`）で持つ。メンバーを「本体 → シーン → パーツ」の順に宣言して、パーツ → シーン → FBX SDK本体の順に解放する（今までと同じ順序）。インポーターは読み込みのブロックの中だけで持ち、ブロックを抜けると解放する（今までと同じ位置）。パーツは`unique_ptr`で持つ。デストラクターは、`FbxParts`が不完全な型のヘッダーでは定義できないので、`Fbx.cpp`に置いた。空の`Release()`は消した。
- `Audio`: XAudio本体は`ComPtr`、ボイスは`DestroyVoice()`を呼ぶ削除関数（`VoiceDestroyer`）付きの`unique_ptr`、波形データは`unique_ptr`。`AudioData`のメンバーを「波形データ → サウンド情報 → ボイス」の順に宣言したので、ボイス → 波形データの順に解放される（ADR-0004の「ソースボイスを先に破棄する」を、型で守る形にした）。`AllRelease()`は、サウンド → マスターボイス → XAudio本体の順を、今まで通り明示している。ボイスの数は`voices.size()`で数えるので、`svNum`のメンバーは消した。読み込みの途中で失敗したときの、作りかけのボイスの手動の破棄も、いらなくなって消した。
- そのままにしたもの: `Text::Release()`は`Image`の番号を手放す処理、`Model` / `Image` / `Audio`の`Release(…)` / `AllRelease()`はシーン切替や終了のたびに呼ばれる公開の関数なので、残した。
- 区切り②の対象は、D3D・FBX SDK・XAudio2に依存するので、テストには入れていない（CIにはFBX SDKがないため）。代わりに、確認用のビルドで確かめた。

### 確かめたこと（区切り②）
- テストのDebug・Releaseのビルドと全件合格（58件・256の検証）。クリーンクローンでのCI相当のビルドとテストも合格。ゲーム本体とテストを含むソリューション全体のリビルド（Debug・Release）で、エラー0、警告は基線と同じ（`C4244`×25、`X3206`×7、`C4305`×1）。
- Assetsの全部を、実際の読み込みの経路で読んだ結果が、区切り①の終わりと同じ。FBX19個（頂点・インデックス・マテリアル・骨・ウェイトのハッシュ）、画像48回（大きさ）、WAV13個（波形データのSHA-256を、別に実装した解析と照合）。骨のあるモデルは、アニメーションの4つのフレームで変形させたあとの頂点のハッシュまで同じ（変形の経路が、数値で同じ）。
- 終了時のメモリリーク（CRTの報告）が0ブロック。D3Dのデバッグレイヤーで、デバイスを解放する直前に生きているオブジェクトを調べて、デバイスとコンテキストの2つだけ（テクスチャ・バッファ・ビュー・サンプラーが残っていない）。実行中ずっとのデバッグレイヤーのメッセージは、すでに知られている深度ステンシルステートの作成失敗の8件だけで、区切り①の終わりと同じ。
- 検出できることの確認: わざと`Image::AllRelease()`を何もしないようにした版では、デバッグレイヤーの報告が、バッファ30・シェーダーリソースビュー10・サンプラー1の残りを検出した（正常時は残らない）。CRTの報告は、この場合も0ブロックのままだった（プールは静的な変数で、CRTの報告より前の終了処理で解放されるため）。解放し忘れの検出には、デバッグレイヤーの報告のほうが効く。
- シーンの自動巡回（2周）を、基線と交互に走らせて、タイトル・ゲーム選択・散歩（プレイ）・ゲームオーバーの画面が、画素まで基線と一致した（犬の選択の画面は、基線どうしでも毎回変わるので比べていない）。
- VFX（エミッターの開始と終了、パーティクルが消えるまでエミッターが残ること、終了時に生きているエミッターとパーティクルの解放）を動かして、現存数の推移が基線と同じ（26 → 41 → 0 → 50）。読み込めない画像のビルボードの警告も同じ。
- 失敗の注入の結果が、基線と同じ。必須のモデルが欠けたとき（3パターン）は、ダイアログを出して終了コード1。壊れたWAV（ファイルなし・0バイト・テキスト・先頭で切れている・dataの途中で切れている）と、画像が欠けた・0バイト・PNGではないとき（警告を残して続行）。画像が欠けたとき、マゼンタの代替画像が実際に描かれていること（タイトルの画面で17,994画素。基線と同じ）。
- 起動して8秒動かして、終了コード0、警告は既知の2件だけ。

### 見つけたが直していないこと（区切り②）
- `FbxParts::InitSkelton`の`polyTable`（頂点からポリゴンを逆引きする表）は、作るだけで使われていない。頂点数×ポリゴン数の二重ループで、骨のあるモデルの読み込みを遅くしている。`vector`に置き換えただけで、残した。
- `VFX::Start`のハンドルは「そのときのエミッターの数」なので、途中のエミッターが消えたあとに作ると、残っているエミッターと番号が重なることがある（`End`は、見つかった先頭の1つだけを止める）。
- 一緒に直ったもの: `FbxParts`のデストラクターが、`new[]`で作ったインデックスの配列を`delete`（`[]`なし）で消していた（未定義の動き）。`InitIndex`の`ZeroMemory(&pIndex[i], …)`が、マテリアルの数がポリゴン数×3を超えると、配列の外を書く可能性があった。どちらも`vector`にして、なくなった。頂点の配列が0で初期化されるようになった（今までは、どのポリゴンからも使われない頂点は不定の値だった。描画には使われない）。

### 残り
- 区切り③（COMと後始末）: `Direct3D`と`Input`のCOM、`CsvReader`の一時バッファー、`SAFE_DELETE` / `SAFE_DELETE_ARRAY` / `SAFE_RELEASE`の削除、ドキュメント。
